Writing SPINS — automatic numbering

Writing SPINS

Write instructions in their reading order. Nest related instructions under a section or paragraph. The generator assigns all printed numbers, contents entries, table and figure captions, and citation numbers.

kind: spins
schema_version: '0.3'
scope: standing
meta:
  id: squadron-standing
  title: Special Instructions
  revision: '1'
content:
  - kind: section
    title: Airfield procedures
    blocks:
      - kind: paragraph
        id: north-field-arrival
        lead: NORTH FIELD arrival.
        text: Coordinate your arrival with local control.
      - kind: paragraph
        text:
          - text: 'For arrival coordination, see '
          - target: north-field-arrival
          - text: '.'

The section becomes 1. Its paragraphs become 1.1 and 1.2. The link prints Paragraph 1.1. Insert another paragraph before the arrival procedure and the reference becomes Paragraph 1.2 automatically. An id is optional unless you need to link to or amend that block. Use a descriptive name, never a printed number.

Content

kind Required content Use
section title, blocks Group related instructions; nest to any supported model depth.
paragraph text Prose, optional emphasized lead, and optional nested blocks.
list items Each item has text and optional blocks; choose a marker style.
table caption, columns, rows Each column has key and heading; each row supplies exactly those keys.
source_table caption, source, columns Build a table from an existing typed data source. Each column also selects a scalar field.
figure caption, alt, src Embed a local image. Optional width_percent controls its width.
note text A numbered note with an optional heading.
reference reference Display an entry from meta.references.

A section's optional role is section, part, annex, or appendix. Parts use Roman numerals; annexes use letters; appendices use decimal numbers. Each starts a local hierarchy. References include the enclosing scope, such as Part III, Paragraph 2.1. Ordinary sections, paragraphs, and lists share a decimal sequence. Tables, figures, notes, and bibliography entries have separate document-wide counters. A table between two paragraphs does not create a gap in the paragraph numbers.

List styles are bullet, decimal, lower_alpha, upper_alpha, lower_roman, and upper_roman. Markers are automatic; start is optional and defaults to 1. Numbered descendants inside a list item extend the list number with the item's ordinal position. Markdown uses embedded HTML for lists so these styles and nested mixed content survive export.

Text and references

Use a plain string for normal prose. For formatting or links, use a list of text runs:

text:
  - text: 'Check-in. '
    marks: [bold, underline]
  - text: 'Use the channel in '
  - target: exercise-channels
  - text: '; consult '
  - citation: exercise-brief
  - text: ' for the complete briefing.'

Marks are bold, italic, underline, and code. Text runs preserve spaces, so quote leading or trailing spaces. A target links to a block's id. A citation links to an id in meta.references. The generator supplies visible reference numbers. Optional text on either link supplies descriptive wording when needed. Literal text is escaped; it is not interpreted as HTML.

Reusing standing instructions

A mission document sets scope: mission, an effective period with timezone offsets, and a base with the standing document's id, exact revision, and relative path. Its changes can:

  • add a block at the root or inside a section/paragraph identified by parent; optional before or after selects a sibling anchor.
  • replace a target with a block that retains the target's id.
  • remove a target.

Amendment targets, parents, and insertion anchors refer to baseline identifiers. Added blocks use new identifiers; replacements may retain identifiers from their own replaced subtree. Repeated additions after the same anchor retain their authored order. Conflicting writes, broken references, and mismatched baseline revisions fail validation. Mission content appends to the composed baseline; use an insertion amendment to put a mission part first. Numbering runs after composition. The standing source stays unchanged.

Baseline bibliography entries carry forward; conflicting definitions fail. Classification and handling carry forward when absent from the mission metadata. Presentation fields inherit unless the mission overrides them. Other mission metadata is authored on the mission document.

The existing !include and variables loader is available. Image and source-table paths resolve relative to the SPINS file that owns them, including its standing baseline. An included fragment uses its owning SPINS file's asset directory. Supported image extensions are PNG, JPEG, GIF, WebP, and SVG. HTML embeds images and CSS; PDF uses that same rendered document. Markdown image data URLs require viewer support.

ATO proposal rules and design

ATO authoring proposal 0.2

SPINS publication support is now schema 0.3 in the application. Read the SPINS authoring guide in this reader. The ATO proposal has not been integrated with that implementation; its provisional SPINS reference fields remain subject to revision.

This specification replaces the earlier 0.1 proposal. The contract consists of ATO JSON Schema, resource JSON Schema, their Pydantic models, and the semantic validator. The complete field reference defines every field, required value, variant, catalog, and referenced type. There are no placeholder payload types in the schemas.

The contract describes DCS briefing data. ATO tasking is modeled as missions with participating flights. Each flight has an expected aircraft configuration, initial fuel plan, launch plan, and recovery plan. Mission variants add their required target, area, timing, collection, support, or transport information. Readability and reuse come from named catalogs and the existing YAML include/variable loader.

Scope and ownership

Mission Mission number, typed tasking, participating flights, control, priority, package association, supporting requests, threats, support links, contingencies, constraints, briefing attachments

The OPORD remains an independent document. The proposal reuses its AirspaceControl, Weather, ReportDefinition, ClassificationLevel, and DesiredEffect definitions. A JPITL entry is a targeting-list record with approval and prioritization information; it is not forced into the role of a geometric target definition. Target sources can cite the existing list record. No duplicate OPORD rendering implementation is introduced.

Exact root contracts

ATO requires kind: ato, schema_version: '0.2', meta, period, resources, and a nonempty missions list. meta requires id, title, and revision. period requires absolute start and end timestamps with UTC offsets. Optional root fields are spins, packages, weather, and general_instructions.

The shared resource object contains typed maps named places, areas, channels, agencies, stores, scls, targets, threats, routes, reports, and procedures. It also accepts the existing airspace object. Empty unused catalogs are allowed. Each reference field names its catalog in the generated JSON Schema using x-catalog; the semantic validator checks those declarations.

All model fields and alternatives are listed in the field reference. Fields are not silently accepted under a generic extension dictionary. Structured identifiers, units, closed alternatives, and reference categories have declared contracts. Prose remains open text where the content is genuinely an instruction or description.

Mission task variants

All task variants require objective and success_criteria. All provide abort_criteria and report_refs. Each variant then requires the following task-specific content:

Kind Task-specific required fields
preplanned_attack role, nonempty assignments; each assignment requires a target selection, assigned flights, desired effect, success criteria, and timing
on_call_cas Supported force, area, availability, tasking agency, target-assignment procedure, check-in procedure, terminal-control policy
cap Area/station, altitude block, station window, coverage responsibility, engagement instructions, handover
escort Supported missions, rendezvous place/time, protection window, separation instructions, release condition
refueling Area/track, altitude block, station window, method, planned offload, channel, rendezvous procedure; receiver slots or an explicit unassigned-receiver policy
airborne_control Area/station, altitude block, station window, control responsibilities, handover
reconnaissance Nonempty collection requirements and reporting procedure; each collection requirement includes information, sensor, area, window, final-product deadline, product, recipient
electromagnetic Area, operating window, supported missions, assigned effect, equipment requirements, coordination procedure, restrictions
transport Pickup/destination, pickup/delivery time constraints, manifest, delivery method, ground coordinator, loading procedure
personnel_recovery Incident, search area, availability, coordinator, tasking procedure, recovery method/destination, medical requirements, recognition procedure
training Area, exercise window, event steps, restrictions, debrief procedure
custom Name, area, operating window, assigned action steps, coordination, required capabilities

preplanned_attack.role distinguishes strike, SEAD, DEAD, preplanned CAS, and maritime attack. A custom task still has mandatory timing, area, action, coordination, and completion information; it cannot degrade to a role label and an objective alone.

There is one valid authored example for each of the 12 task variants. The combined example contains every variant and includes a carrier-based training element, helicopters, tanker/control aircraft, scheduled departures, alert launches, airborne starts, and a midnight crossing. Its values are illustrative schema fixtures, not verified simulator payloads or flyable mission files.

Targets and assigned effects

A fixed target requires at least one named aimpoint. Each aimpoint requires a name, description, geographic position, and elevation in feet MSL. Optional DCS object references and attachments support mission-editor identification and briefing products.

A mobile target requires a search area, expected movement, and identification features. Its optional last-known position is inseparable from an observation timestamp. An area target requires the area, target-population description, and identification features. The schema does not invent an aimpoint for these target types.

A target selection declares fixed, mobile, or area kind. Fixed selections specify aimpoint identifiers. The validator confirms that the selected target has the matching kind and that every aimpoint exists. Every attack assignment names participating flights from its own mission. Member selectors, when supplied, identify aircraft within those flights; omission selects all members.

Desired effects reuse the repository's DesiredEffect vocabulary. Assignment-specific effects, timing, and constraints remain in the mission. They do not overwrite reusable target data. Alternate assignments require an explicit activation condition. Required-store identifiers can state mission-specific equipment needs, and the validator checks their presence in each selected member's primary effective SCL. This is an inventory check, not a weaponeering or sufficiency calculation.

SCL and aircraft configuration

The selected primary SCL is mandatory for every flight. An SCL declares aircraft compatibility by explicit aircraft-type names. Primary, secondary, alternative, and member-override selections are checked against that declaration. The validator does not infer compatibility from similar display names or an installed DCS module database.

An SCL contains exactly one payload representation:

Kind Authoritative content
summary Store identifiers and per-aircraft quantities, with optional fuze, laser-code, or program text
stations Unique station identifiers, optional rack identifiers, and the store items carried at each station
clean Explicitly no external payload

Gun ammunition and countermeasure-program instructions are separate optional SCL fields. A summary can be derived from station loads. A second conflicting handwritten summary is not accepted. A store catalog item identifies weapon, pod, tank, rack, cargo, or other equipment and may preserve a DCS CLSID. The schema does not certify pylon fit, rack compatibility, aircraft limits, or simulator weapon-program behavior.

Configuration.primary_scl is the expected complete configuration. A secondary_scl requires secondary_purpose; the two payloads are not silently combined. This project field does not claim to implement every military interpretation of SCL1/SCL2. Alternative configurations require a condition and authority. Member overrides may change SCL, fuel, identification, or DCS unit association for an individual aircraft. Duplicate or out-of-range members are rejected.

SCLs describe equipment. Flight fuel plans describe expected fuel. This prevents a change to a sortie fuel requirement from changing a shared weapons configuration. Fuel supports mass in kilograms or pounds, or explicit internal/external fuel percentages for the initial state. Joker, bingo, and reserve thresholds use masses and are compared after unit conversion. The validator checks their ordering.

Flight execution and support

Launch is scheduled, alert, or airborne. Scheduled launches specify a departure and takeoff time, with optional startup/taxi times. Alert launches specify departure, availability, readiness minutes, and release authority. Airborne starts specify position, time, altitude, and speed. Recovery specifies a destination, with optional expected time, alternates, procedure, and restrictions.

Routes contain ordered points with identity, name, position, action, and altitude. Speed, timing, and instructions are available per point. Flight activities record transit, hold, station, refueling, task, recovery, or other execution phases. Repeated station or refueling periods fit within the same flight assignment. A flight may select an alternate route through a contingency with a condition, action, and decision authority.

Radio assignments refer to channel definitions and may specify aircraft radio and preset. Identification fields cover mode 1/2/3 codes, mode 4/5 instructions, TACAN, and datalink identification. The new contracts preserve string codes with leading zeros. Place data can describe airfields, carriers, FARPs, and points, with optional coordinates, elevation, runways, control, TACAN, approaches, and DCS references.

Mission control is either a named agency or an explicitly self-controlled flight with instructions. Support links identify a provider flight, role, coordination instructions, and optional window. The validator checks provider existence and task-role agreement. Refueling receivers require a declared compatible method, a slot inside the tanker window, and an allocation within planned offload. Module-specific capability and fuel-feasibility checks remain outside this authoring validator.

Packages group missions through references. A package has a name, objective, and commander drawn from a flight in that package. Display order comes from authored lists. Identifiers do not depend on callsign spelling or display numbering. A mission can explicitly appear for coordination only.

Validation and reproducibility

The ATO model remains an external prototype. Its schemas enforce structural requirements, closed variants, units, bounds, payload exclusivity, fuel ordering, and launch alternatives. Prototype validation checks catalog references, target/aimpoint identity, SCL compatibility, aircraft members, package membership, mission support, tanker allocations, and time ordering. Those checks do not establish integration with the application's SPINS 0.3 implementation.

The current SPINS contract and repository verification tasks appear in the SPINS guide and requirements in this reader.

Research traceability and limits

The public ATOCONF example identifies mission, aircraft, SCL, target/aimpoint, time, control, reconnaissance, and refueling information. This proposal now assigns each concept an explicit owner and a defined type. The historical example is a domain source, not a current USMTF conformance specification. US Air Force, AFDD 2-1, 22 January 2000, Appendix F.

The 2025 CASPOA handbook shows separate aircraft mission/aircraft information and repeated mission-location segments. Those concepts inform participating flights and repeated activities. CASPOA, 2025 public student handbook, pages 41–42.

The current AJP-3.3 distinguishes baseline and ATO-period SPINS, and recognizes coordination-only ATO entries. Those concepts inform applicability, baseline references, and tasking relationships. NATO, AJP-3.3 Edition C Version 1, February 2026, pages 18 and 46.

The field names, mandatory authoring requirements, task union, and catalog relationships are explicit project design decisions. The public sources do not establish them as one universal military template. MIL-STD-6040 remains a separate interoperability requirement with access and edition limitations recorded in the DLA catalog.

This is complete as a defined and executable authoring contract for the declared scope. It is not proof of military interchange compatibility, flight feasibility, weapon suitability, simulator payload compatibility, or terrain correctness. It does not parse or generate .miz files, compute target/weapon pairings, implement DCS Lua APIs, or provide application renderers. Geometry validation checks representation and basic bounds; it does not perform full polygon topology or airspace-conflict analysis. Cited documents and attachment paths are preserved as references, not automatically fetched or verified. Existing imported OPORD types retain their existing validation behavior.

Requirements and acceptance criteria

SPINS publication support

Purpose and scope

Provide SPINS authoring and Markdown, HTML, and PDF generation in the application. Preserve the numbered publication structure observed in the researched military examples. The earlier external v0.2 proposal is not a deployed compatibility contract; this publication schema is version 0.3.

Definitions

A block is a section, paragraph, list, table, figure, note, or bibliographic reference. A section or paragraph can contain nested blocks. An optional block identifier is a stable name for links and amendments. Printed numbers are generated from the effective document hierarchy. A mission SPINS document may amend one complete standing baseline.

Known inputs and constraints

Use the existing Pydantic base, YAML include/variable loader, data-source registry, Jinja templates, and WeasyPrint. Preserve existing OPORD, FRAGO, and WARNO behavior. Do not add production dependencies. Keep prose as authored; do not infer a universal chapter list or operational rules.

Requirements and acceptance criteria

ID Requirement Acceptance criterion / method
SPINS-001 The document shall preserve authored block order and nesting. Render a seven-level hierarchy with interleaved block kinds; test.
SPINS-002 The renderer shall generate publication numbering from the effective hierarchy. Insertion/removal updates paragraph numbers, contents, and cross-references in HTML and Markdown; test.
SPINS-003 Rich text shall preserve declared emphasis and references. Render bold, italic, underline, code, internal links, and citations with escaped literal text; test.
SPINS-004 Tables shall validate their row/column contract. Reject missing/unknown cells and duplicate column keys; test.
SPINS-005 Resource tables shall validate data through the existing registry. Render a real typed source and reject invalid field selections; test.
SPINS-006 The document shall reject duplicate identifiers and unresolved references. Exercise nested paragraphs, cells, and notes; test.
SPINS-007 A mission amendment shall pin its standing baseline revision. Reject a wrong revision and non-standing baseline; test.
SPINS-008 Composition shall retain source order and leave input objects unchanged. Replace/add/remove nested nodes and compare both inputs before/after; test.
SPINS-009 Figure paths shall resolve relative to the document that owns them. Baseline and mission figures in different directories embed correctly; test.
SPINS-010 HTML shall embed local figures and styles. Inspect output for data URLs and absence of external stylesheets; test.
SPINS-011 PDF shall provide publication headers and page numbers. Render and inspect a multi-page document; demonstration.
SPINS-012 The CLI shall expose SPINS rendering and JSON Schema export. CLI tests and named repository tasks.
SPINS-013 The schema reader shall reflect the current SPINS model. Regenerate and check reference closure and browser links; inspection.

Interfaces and data

opord spins INPUT renders the effective document. opord schema --document-type spins exports its JSON Schema. content is an ordered block list. Authors supply hierarchy and prose, never printed labels. Sections, paragraphs, and lists share hierarchical decimal numbering. Parts use Roman numerals; annexes use letters; appendices use decimal numbers. Each part, annex, or appendix starts a local hierarchy, and cross-references include its enclosing scope. Tables, figures, notes, and bibliography entries use independent document-wide sequences. List markers follow the selected style. Numbered blocks inside a list item extend the list number with the item's ordinal position. Inline formatting uses explicit text runs, not raw HTML. source_table reads a standalone data-source YAML through the canonical registry. Figure paths are local files; referenced source-table and figure paths are relative to their owning SPINS document, including baseline documents.

Out of scope and risks

This change does not integrate the ATO prototype, implement USMTF, validate operational policy, or certify DCS flight/payload behavior. It does not attempt to migrate arbitrary v0.2 typed plans automatically into prose. Canonical new examples replace that provisional SPINS representation. Markdown image data URLs depend on the consuming viewer; HTML and PDF are the portable visual outputs.

Research and standards

The design follows the publication structures in the NATO airspace example, U.S. military example, Appendix D, and NATO template, Annex J. These historical examples establish representational needs, not current operating policy or a universal mandatory outline.

Applicable shared standards: RQM-001–007, DM-001–005/017, ARCH-002/014, FUNC-001–005/013, TEST-001–003/007/008/011/019, COMM-015–022. Completion evidence belongs in the final change report.
